# Технический пакет надёжности — отдельная библиотека для проверки

**Это не готовое обновление `beeline.service` и не новая версия `test_beeline.py`.**
Пакет не подключён к установленной программе и сам по себе не меняет поведение бота.
В нём нет установщика, команд `systemctl`, доступа к браузеру, сетевого клиента или ключей.
Ни автозаполнение личных данных, ни подписание, ни обход проверок не реализованы.
Существующие обработчики программы не отключаются и не заменяются.

## Что реализовано

1. `canonical_messages` и `request_payload`: ровно один актуальный `system`, без
   инструкций из checkpoint. Одинаковый построитель для текстового запроса и запроса
   с инструментами. История user/assistant/tool сохраняется. `fingerprint` вычисляет
   хеш фактического системного текста, но не выводит его и не пишет секреты в журнал.
   Сам текст роли должен предоставить вызывающий код — новая миссия не навязывается.

2. `assert_lifecycle_allowed`: проверка запрета разрушительных действий при активной
   защите. `completion_state`: ошибка имеет приоритет, отсутствующее или несвязанное
   подтверждение даёт UNCERTAIN. Флаг доверия нельзя брать из ответа языковой модели:
   источник `CompletionEvidence` должен проверяться отдельным адаптером приложения.
   Эти функции не исправляют автоматически существующий watchdog; без вызова из
   реальных обработчиков они не защищают работающие вкладки.

3. `merge_capture`: дополнение уже собранных значений по явной карте имён полей.
   Непустые значения, в том числе 0 и False, сохраняются. Нет DOM-парсинга,
   поиска паспортных сведений и генерации отсутствующих значений.

4. `Queue`: сохранение полного ответа и всех частей в отдельной SQLite-базе;
   атомарное сохранение входящей пачки и следующего offset; временная блокировка
   части для одного отправителя; отдельный ACK каждой части; повтор с задержкой;
   учёт retry_after; сохранение неотправленных сообщений после перезапуска.
   `send_one` использует переданный вызывающим кодом адаптер sendMessage.
   Повтор с тем же ключом не перезаписывает отправленный ответ.

Дополнительно `session_tail` читает только указанную сессию с отдельным маркером,
не возвращая всю старую историю, когда маркер не найден.

## Проверка без установки

Распаковать ZIP в новую пустую папку и выполнить из этой папки:

```bash
python3 -m unittest -v test_reliability
```

Нужен Python 3.10 или новее. Зависимостей вне стандартной библиотеки нет.
Тесты используют временные базы, фиктивные сообщения и подставной API. Они не читают
`/opt/beeline`, не открывают сайт, не отправляют сообщения и не перезапускают службы.

Локальный результат: 44 теста успешно пройдены. См. `test_results.txt` и
`verification.json` с версией интерпретатора. Синтаксис отдельно проверен на
совместимость с Python 3.10; выполнение на установленном серверном интерпретаторе
и интеграция с текущим проектом не проверены.

## Ограничения, которые важно не путать с исправлениями проекта

- Полного автономного исполнителя и постоянного scheduler заданий здесь нет.
- Нет миграции старой очереди или изменения `processed_numbers.txt` / JSONL.
- Хранилище отказывается открывать постороннюю SQLite-базу. Нельзя направлять его
  на существующую базу приложения. Сообщения хранятся локально открытым текстом;
  шифрование и срок хранения должны задаваться приложением.
- После потери HTTP-ответа Telegram мог уже принять сообщение. Повтор иногда создаст
  дубликат. Гарантия exactly-once не заявляется.
- Длительность сетевого вызова должна быть меньше lease; при зависании и истечении
  lease другой отправитель может получить ту же часть. Устаревший ACK отвергается.
- Постоянные ошибки 400/401/403 удерживают сообщение для проверки, а не удаляют его.
- Ответы отправляются обычным текстом. Перенос разметки HTML/Markdown и entities
  между частями не реализован.
- Адаптер получения updates должен использовать offset только после успешного
  `ingest`. Второй параллельный getUpdates-потребитель здесь не запускается.
- Полное состояние текущей службы, Chromium/CDP, прокси и реальный DeepSeek API
  этими изолированными тестами не подтверждаются.

## Основание API

Официальное описание Telegram Bot API, проверенное 28.09.2026:
https://core.telegram.org/bots/api#getupdates
https://core.telegram.org/bots/api#sendmessage

Именно следующий запрос getUpdates с большим offset подтверждает ранее полученные
updates. Поэтому сначала нужно устойчиво сохранить данные. Для sendMessage проверяется
ok=true и возвращённый message_id. Размеры частей выбраны консервативно; полный текст
не обрезается.
